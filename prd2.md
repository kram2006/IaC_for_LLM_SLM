# PRD — Reliable SLM/LLM IaC Evaluation Framework (Backend-Only)

## 1) Product Overview

Build a reproducible, provider-agnostic backend evaluation framework to benchmark SLMs/LLMs on Terraform generation for Xen Orchestra workflows, with strict task semantics, deterministic execution, and audit-grade reporting.

The framework must evaluate the active **10-task CRUD benchmark** with controlled dependency chains and produce trustworthy pass/fail and pass@k results.

---

## 2) System Goals

1. **Correctness-first evaluation**: no false pass from incomplete validation.
2. **Reproducibility**: same inputs/config should produce comparable outputs.
3. **Provider portability**: OpenRouter, Ollama, LM Studio, HuggingFace supported via explicit adapters.
4. **Chain-aware execution**: enforce required task dependency chains.
5. **Explainable scoring**: every pass/fail decision traceable to checks and artifacts.

---

## 3) Target Users

- AI evaluation engineers benchmarking model quality
- Infra/platform engineers validating Terraform generation reliability
- Researchers comparing prompting and model strategies (baseline, CoT, FSP, repair)

---

## 4) Supported Model Providers

## Required providers (first-class)
1. **OpenRouter**
2. **Ollama** (OpenAI-compatible local endpoint)
3. **LM Studio** (OpenAI-compatible local endpoint)
4. **HuggingFace Inference**

## Provider contract (must be uniform)
- `generate(messages, model, temperature, max_tokens, seed, timeout)`
- retries/backoff with structured error taxonomy
- response capture with raw payload checksum and truncation detection

---

## 5) Evaluation Pipeline Design

## Canonical 9-stage pipeline
1. **Task Resolution**: load task row + strict schema validation.
2. **Prompt Construction**: baseline/COT/FSP/repair composition with immutable template version id.
3. **Model Execution**: provider adapter call with timeout/retry policy.
4. **Output Capture**: raw model text + extracted Terraform code + extraction diagnostics.
5. **Static Validation**: `terraform init/validate/plan` (and apply when mode requires).
6. **Intent/Constraint Validation**: rule engine checks per category + task-specific constraints.
7. **Post-State Validation**: live XO verification for stateful tasks (CREATE/UPDATE/DELETE apply mode).
8. **Metric Computation**: pass/fail labels + pass@k + optional similarity metrics.
9. **Artifact & Metadata Logging**: immutable JSON, logs, plan JSON, manifest.

## Hard rule
- Final success label must require all applicable validation stages to pass.

---

## 6) Task Execution Architecture

## 6.1 Active benchmark scope (must remain default)
- **10 tasks**: `C1.1, C1.2, C1.3, C2.2, C2.3, R1.2, U1.2, D1.2, D2.2, C5.2`

## 6.2 Dependency structure
- **Independent**: `C1.1, C1.2, C2.2, C5.2`
- **Chain A**: `C1.3 -> U1.2 -> D1.2`
- **Chain B**: `C2.3 -> R1.2 -> D2.2`

## 6.3 Execution rules
- Chains are declared in config and validated before run (DAG + allowed transitions).
- Update/Delete tasks cannot execute outside valid prerequisite context unless explicitly run in synthetic-plan mode.
- READ tasks require semantic checks (output/data-source correctness), not only “no changes”.

## 6.4 Workspace isolation
- Workspace key: `{run_id}/{model}/{strategy}/{task_or_chain}/{sample}`
- No reuse across runs unless explicit resume mode.
- Mandatory cleanup policy configurable per mode.

---

## 7) Metrics and Benchmarking Strategy

## 7.1 Core decision metrics
- `task_pass` (boolean)
- `failure_reason_codes` (list)
- `passes_required_stages` (map of stage statuses)

## 7.2 pass@k
- Use unbiased estimator: `1 - comb(n-c, k)/comb(n, k)`
- Report N/A when `n < k`
- Compute separately for:
  - `plan_pass@k`
  - `apply_pass@k`
  - `full_semantic_pass@k`

## 7.3 Similarity metrics (optional, non-gating)
- BLEU / CodeBERT / CodeBLEU can be reported for analysis only.
- Must be generated by one canonical metrics module with versioned config.

## 7.4 Edge-case accounting
- C5.2 (resource exhaustion) must have dedicated label class (expected refusal / expected failure), not merged blindly into normal success buckets.

---

## 8) Data Flow

1. **Input layer**: task CSV + task specs YAML + run config.
2. **Execution layer**: prompt builder -> model adapter -> terraform executor -> XO verifier.
3. **Validation layer**: static + intent + post-state engines.
4. **Aggregation layer**: per-sample records -> per-task aggregation -> per-model summary.
5. **Output layer**:
   - `artifacts/run_manifest.json`
   - `artifacts/tasks/<task_id>/<sample>/...`
   - `results/dataset/<model>/<entry>.json`
   - `results/metrics/<run_id>/summary.json`

---

## 9) Reproducibility Requirements

Mandatory per run:
1. `run_id` (UUID)
2. git commit SHA
3. normalized config snapshot hash
4. dataset hash and task-spec hash
5. dependency snapshot (`pip freeze` or lockfile hash)
6. provider/model version + endpoint
7. seeds used per sample

Determinism requirements:
- deterministic task ordering
- deterministic chain ordering
- explicit random seed policy for all providers that support seeds
- clear non-determinism flag when provider does not support seed

## 10) System Architecture Diagram (Textual)

```text
[CLI Runner]
   -> [Config Loader + Schema Validator]
   -> [Task Scheduler]
       -> [Chain Validator / Dependency Manager]
       -> [Workspace Manager (isolated run paths)]
       -> [Prompt Engine]
       -> [Provider Adapter Layer]
            |- OpenRouter Adapter
            |- Ollama Adapter
            |- LM Studio Adapter
            |- HuggingFace Adapter
       -> [Terraform Executor]
            |- init/validate/plan[/apply]
            |- plan-json exporter
       -> [Validation Engine]
            |- Task Spec Rule Validator
            |- READ semantic validator
            |- Post-state XO validator
       -> [Result Assembler]
            |- per-sample artifact pack
            |- canonical task JSON
   -> [Metrics Engine]
       |- pass/fail aggregations
       |- pass@k estimator
       |- optional similarity metrics
   -> [Reporting Layer]
       |- run manifest
       |- model leaderboard
       |- audit logs
```

## 11) Future Improvements

1. Add pluggable policy backend (OPA/Rego mode) for richer intent checks.
2. Add confidence intervals/bootstrap reporting for pass@k.
3. Add distributed execution with isolated infra sandboxes for higher-scale sampling.
4. Add regression dashboard (metric drift by commit/run).
5. Add strict CI gates: dataset schema checks, provider smoke tests, chain integrity tests.

---

## Acceptance Criteria (Release Gate)

1. All 10 tasks run with correct chain behavior and deterministic artifacts.
2. No task marked pass without passing all required validation stages.
3. pass@k reports are statistically correct and mode-separated (plan/apply/full semantic).
4. Provider adapters for OpenRouter/Ollama/LM Studio/HF pass smoke tests.
5. Re-running the same config produces traceable, comparable outputs with full manifest metadata.
